# REVIEW.md

List every defect you found in the starter `app/main.py` (helpers and endpoints). For each one:

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How you fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` (lines 33-37) | `int((punch_in - start).total_seconds() / 60) > 10` truncated seconds before checking grace. A punch-in at 09:40:01 for a 09:30 shift has elapsed 601s (10 min 1 sec); integer division gave 10, and `10 > 10` was False, returning 0 instead of 10. Also replaced hour/minute directly on punch_in ignoring IST. | Input `punch_in` = 09:40:01 IST with `shift_start` = 09:30. Function returns `0` instead of `10` (violates R2). | Checked difference in seconds: `diff_sec > 600`. If True, return `int(diff_sec // 60)` elapsed from shift start in IST. |
| 2 | `compute_work_hours` (lines 40-41) | Python's built-in `round()` uses banker's rounding (round half to even) instead of strict round-half-up specified by R4. | Input duration of 7650 seconds (2.125 hours). `round(2.125, 2)` gives `2.12` instead of `2.13`. | Implemented `Decimal.quantize` using `ROUND_HALF_UP` on exact seconds divided by 3600. |
| 3 | `compute_overtime` (lines 44-47) | Did not enforce the 30-minute minimum threshold (R3). Any positive minutes after shift end were returned. Also assumed shift end falls on the same calendar day `date_str`, breaking overnight shifts (R1). | Punch out at 18:45 for an 18:30 shift returned 15 min overtime instead of 0. For overnight shift (22:00 - 06:00), shift end was treated as past morning, producing ~24 hours overtime. | Added `>= 1800` seconds check; for overnight shifts (`shift_end <= shift_start`), advanced shift end to `date + 1 day`. |
| 4 | `health` (lines 72-74) | Returned `{"status": "ok"}` unconditionally without checking MongoDB connectivity or pinging the database. | Stop MongoDB and send `GET /health`. Returned `200` instead of `503 Service Unavailable`. | Added `client.admin.command("ping")`; if ping fails or client is not connected, raise HTTP 503. |
| 5 | `create_employee` (lines 77-85) | Check-then-insert (`find_one` then `insert_one`) has a concurrency race condition. Also `created_at` was naive local datetime and serialized as ISO string rather than integer epoch milliseconds. | Two simultaneous requests to `POST /employees` with the same `emp_code` both succeeded with 201; response schema validation failed on `created_at` being a string instead of epoch ms. | Created unique index on `emp_code` at startup, caught `DuplicateKeyError` and raised 409. Stored UTC datetime and returned epoch milliseconds. |
| 6 | `EmployeeIn` model (lines 53-60) | Lacked schema validation for `emp_code` pattern (`EMP\d{4,6}`), email regex, string lengths, and did not validate that `shift_start != shift_end`. | POST with `shift_start="09:30"` and `shift_end="09:30"` or invalid email succeeded with 201 instead of 422. | Added Pydantic field constraints, regex patterns, and a model validator ensuring `shift_start != shift_end`. |
| 7 | `list_employees` (lines 88-96) | (1) Pagination calculation was `skip = page * page_size`, which skipped page 1 entirely (`page=1` skipped 20 items). (2) `total` counted the whole collection ignoring `department` filter. (3) Omitted sorting by `emp_code` ascending. (4) Returned BSON dates for `created_at`. | `GET /employees?page=1` returned items starting at index 20; `total` did not match filtered count; items were unordered. | Set `skip = (page - 1) * page_size`, filtered `count_documents(q)`, added `.sort("emp_code", 1)`, and converted `created_at` to epoch ms. |
| 8 | `punch_in` (lines 99-105) | (1) Did not check if employee existed before accessing `emp["shift_start"]`, throwing an unhandled `TypeError` (500). (2) Check-then-insert race condition allowed duplicate punches. (3) Ignored IST timezone and overnight shift date rules (R1). | (1) Punch in for unknown employee yielded 500 instead of 404. (2) Parallel requests for same employee and date both succeeded. (3) Punch in at 01:00 IST for a 22:00-06:00 shift got today's date instead of previous day. | (1) Added 404 check for employee. (2) Created unique compound index on `(emp_code, date)` and caught `DuplicateKeyError` -> 409. (3) Implemented `calculate_attendance_date` with IST and overnight shift logic. |
| 9 | `punch_in` (lines 118-121) | Injected `id = str(res.inserted_id)` into response document, violating the `AttendanceRecord` schema. Also returned datetime objects instead of epoch milliseconds. | Client response contained unwanted `"id"` field and `punch_in` was ISO string instead of integer epoch ms. | Removed `_id` and `id`, formatted all instants to epoch milliseconds in `sanitize_attendance_doc`. |
| 10 | `PunchInIn` model (lines 63-66) | `punched_at` did not validate epoch milliseconds range (>= 100000000000) or reject seconds/floats/strings. `status` was unvalidated string, allowing `ABSENT` or invalid strings. | POST with `punched_at=1783312500` (seconds) or `status="ABSENT"` was accepted instead of returning 422. | Added `strict=True`, `ge=100000000000, le=4102444800000`, and restricted `status` to `Literal["PRESENT", "WFH", "ON_DUTY"]`. |
| 11 | `list_attendance` (lines 124-150) | Loaded entire collection into Python memory (`list(db.attendance_logs.find(q))`) and sorted in Python. Also lacked secondary sort by `emp_code` asc, did not validate `date_from <= date_to`, and injected `id`. | High latency / OOM on large datasets (~100k docs); `date_from > date_to` returned 200 instead of 422; items not sorted by `emp_code` on equal dates. | Replaced in-memory sorting with database cursor `.sort([("date", -1), ("emp_code", 1)]).skip(...).limit(...)`; added 422 check for invalid date range; removed `id`. |
| 12 | App startup & Indexes | Starter did not create any indexes on application startup, leaving the database unindexed. | Explain plans showed COLLSCAN across all queries; duplicate key constraints could not be enforced by the database. | Added FastAPI `lifespan` handler that idempotently creates indexes on startup (`emp_code` unique, `(emp_code, date)` unique, `(department, joined_on)`, `(date, emp_code)`, `(date, late_minutes)`). |
| 13 | Instant truncation (R1) | Instants were not truncated to whole seconds before computation and storage (e.g., fractional seconds/milliseconds remained). | A punch-in at 09:40:00.900 retained subseconds in calculation. | Added `epoch_ms_to_datetime_utc` which truncates milliseconds: `(ms // 1000) * 1000`. |

## Items examined and confirmed NOT to be defects
1. **PyMongo client connection setup**: `MongoClient` with environment variable fallback (`os.environ.get`) is correct, ensuring environment variables take precedence over defaults while remaining functional locally.
2. **FastAPI standard error envelope**: Using default FastAPI error responses `{"detail": ...}` conforms directly with openapi.yaml specification for 404, 409, and 422.
3. **Use of `fromisoformat` for dates**: In Python 3.11+, `date.fromisoformat('YYYY-MM-DD')` is built-in, robust, and correctly parses calendar dates.
